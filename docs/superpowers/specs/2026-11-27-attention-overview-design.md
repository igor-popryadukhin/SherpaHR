# Дизайн: обзор «Требует внимания» и восстановление комментариев

Дата: 2026-11-27
Задание: `task_v7.md`, версия `d85eb5e76bd0c839798ec55d21c7f0745b6f995f`.
Ветка решения: `feat/attention-overview` в форке `igor-popryadukhin/SherpaHR`.

## Контекст

Анна руководит несколькими активными проектами. Сейчас, чтобы понять, где нужно
её вмешательство, она открывает каждый проект и читает задачи и обсуждения.
Причины препятствий команда описывает свободным текстом; формальной эскалации
в продукте нет. Добавление комментариев в исходной реализации возвращает 501,
хотя клиент уже умеет отправлять ответ и сохранять несохранённые правки задачи.

## Цель

Дать Анне один экран «Требует внимания» со списком незавершённых задач из
активных проектов, которыми она руководит. В строке видны проект, исполнитель,
срок и причины попадания. Клик открывает существующую карточку задачи с полной
перепиской, формой ответа и редактированием; после закрытия Анна возвращается
к обзору. Параллельно восстановить сохранение комментариев — это обязательное
требование задания.

## Границы

Входит в объём:

- серверный запрос обзора с проверкой руководства и членства;
- экран «Требует внимания» и переход в карточку задачи;
- сохранение комментария с автором и ответом 201;
- исправление карточки, которая сейчас берёт участников и права из выбранного
  проекта, а не из проекта открытой задачи;
- исправление списка задач проекта, который скрывает задачи без исполнителя;
- тесты, документация и проверка сценария на чистой демо-базе.

Не входит в объём:

- настоящая аутентификация, управление проектами и участниками;
- уведомления, фоновые задания и автоматическое обновление по таймеру;
- формальный процесс эскалации;
- NLP/ML-определение просьб о помощи;
- изменение модели задачи или статусов.

## Подходы

**A. Клиентская агрегация.** Angular загружает проекты, затем задачи каждого
проекта, затем комментарии каждой задачи и сам вычисляет причины. Плюс — нет
нового API. Минусы: N+1 запросов, дублирование проверок доступа на клиенте,
медленно и противоречит требованию «один серверный запрос». Отклонён.

**B. Отдельный серверный запрос (выбран).** `GET /api/attention` за один вызов
проверяет права и отдаёт задачи с причинами и цитатой. Клиент только отображает.
Плюсы: единое место для правил доступа и причин, один запрос, простой клиент.
Это вариант, предложенный в запросе.

**C. Материализованный флаг `needs_attention`.** Обновлять флаг при изменении
задач и комментариев. Плюс — быстрый чтение. Минусы: триггеры/фоновые
пересчёты, риск рассинхронизации, лишняя сложность для демо. Отклонён.

## Решения

### Какие проекты и задачи попадают в обзор

- Проект активен: `projects.archived = 0`.
- Текущий пользователь — руководитель: `projects.owner_id = текущий`.
- Текущий пользователь — участник: есть запись в `project_members`.
- Задача не завершена: `tasks.status <> 'done'`.
- Исполнитель любой, включая `assignee_id IS NULL`.
- Архивные проекты и чужие проекты не раскрываются.

Проверка руководства и членства выполняется на сервере, а не на клиенте.

### Причины попадания

У задачи может быть несколько причин; в ответе они идут в фиксированном порядке.

1. **`blocked`** — `status = 'blocked'`.
2. **`overdue`** — `due_at IS NOT NULL` и `due_at < сейчас UTC`. Дополнительно
   отдаётся `overdue_days` — целое число полных суток просрочки (0, если меньше
   суток). Срок без времени не поддерживается моделью.
3. **`help_request`** — в комментариях других участников за последние семь дней
   есть явная формулировка просьбы о помощи. Комментарии текущего пользователя
   не учитываются. Берётся самый свежий подходящий комментарий; в ответе —
   `help_quote` с `comment_id`, автором, временем и фрагментом текста.

Задача попадает в обзор, только если есть хотя бы одна причина. Задача без
срока, без блокировки и без свежей просьбы не показывается.

### Правило явной просьбы о помощи

Ограниченный набор формулировок, регистронезависимо, с учётом Unicode:
«нужна/нужно/нужен … помощь/решение/ответ», «прошу помощи», «требуется помощь»,
«помоги/помогите», «подскажи/подскажите». Отрицание не считается просьбой:
«не нужна помощь», «не требуется помощь», «не прошу помощи» отбрасываются
проверкой отрицания перед найденной формулировкой.

Берётся самый свежий подходящий комментарий. Более свежий нейтральный
комментарий не отменяет найденную просьбу: правило ищет просьбу в окне, а не
оценивает, решена ли проблема. Поэтому в строке показывается цитата — фрагмент
вокруг найденной формулировки (примерно 80 символов до и 120 после, с
многоточиями, без разрыва UTF-8), и решение остаётся за Анной.

Окно — семь дней от текущего времени UTC. Это допущение фиксируется в итоговом
отчёте. На долгоживущей демо-базе засеянные просьбы старше семи дней перестанут
попадать в обзор; для демонстрации нужна свежая демо-база или новый комментарий.

### Сортировка

Сначала задачи с большим числом причин, затем по сроку (раньше — выше, задачи
без срока — в конце), затем по `id`. На свежих демо-данных это даёт порядок
№5 (блокировка + просрочка), №1 (блокировка + просьба), №2 (просрочка),
№7 (просьба). Порядок — продуктовое допущение, его легко изменить.

### API

`GET /api/attention` — один запрос, ответ `{"data": [...]}`.

Элемент ответа:

```json
{
  "id": 5,
  "project_id": 2,
  "project_name": "Автоматизация отчётности",
  "title": "Получить доступ к источнику",
  "status": "blocked",
  "assignee_id": 2,
  "assignee_name": "Борис · разработчик",
  "due_at": "2026-11-25T08:00:00Z",
  "reasons": ["blocked", "overdue"],
  "overdue_days": 2,
  "help_quote": null
}
```

Для просьбы о помощи:

```json
{
  "help_quote": {
    "comment_id": 6,
    "author": "Борис · разработчик",
    "created_at": "2026-11-25T08:00:00Z",
    "excerpt": "Анна, помоги определить ответственного между командами."
  }
}
```

`assignee_name` равен `null` для задачи без исполнителя; клиент показывает
«Не назначен». Фрагмент цитаты — окно вокруг найденной формулировки (примерно
80 символов до и 120 после), с многоточиями и без разрыва UTF-8.
Описание маршрута добавляется в `docs/api.md`.

### Восстановление комментариев

`POST /api/tasks/{id}/comments` сохраняет комментарий от текущего демо-
пользователя. Существующие проверки доступа, архива, JSON и длины текста
сохраняются. Ответ — `201` с полной записью комментария, включая `author` и
`created_at`. Версия задачи не меняется. Клиентский `addComment()` уже умеет
добавлять ответ в обсуждение, не затирая несохранённые поля задачи, — его
менять не нужно.

При сохранении существующей задачи из обзора проект берётся из
`detail.project_id`, а не из выбранного в боковом меню. После успешного
`PATCH` обзор обновляется; завершённая задача исчезает из списка.

### Список задач проекта

Убрать `JOIN users u ON u.id = t.assignee_id` из `GET /api/projects/{id}/tasks`.
Сейчас он скрывает задачи без исполнителя, в том числе №7. Клиент уже умеет
показывать «Не назначен».

### Карточка задачи

Карточка должна брать участников, признак архива и права из проекта открытой
задачи, а не из выбранного в боковом меню. Для существующей задачи источник —
`detail.project_id`; для новой — выбранный проект. Это исправляет открытие
из общего списка, когда выбран другой проект или не выбран ни один.

### Интерфейс

- В боковом меню над списком проектов — пункт «Требует внимания» со счётчиком;
  при пустом списке пункт не показывается. Если обзор уже открыт и список
  опустел, остаётся пустое состояние.
- Основная область: заголовок, краткое пояснение правил и таблица.
- Колонки: проект, задача, исполнитель, срок, причины.
- Причины — цветные метки: «Заблокирована», «Просрочена» (с числом дней),
  «Просьба о помощи».
- Под названием задачи с просьбой — цитата с автором и временем.
- Клик по названию открывает существующую карточку. Карточка показывает
  проект задачи; после закрытия возвращает туда, откуда открыта.
- После сохранения задачи обзор обновляется: завершённая задача исчезает.
- Смена демо-пользователя очищает список обзора, перезагружает контекст,
  проекты и обзор; открытая карточка закрывается. Запоздавшие ответы старых
  запросов отбрасываются по счётчику поколений. Если текущий экран — обзор,
  он остаётся открытым.
- Пустое состояние: «Сейчас задач, требующих внимания, нет».

Текстовый набросок строки:

```text
Автоматизация отчётности   Получить доступ к источнику   Борис  25.11.2026  [Заблокирована]
                           #5                            · разработчик  [Просрочена · 2 дн.]
```

## Проверки

### Smoke-тест API

Дополнить `backend/tests/smoke.php`:

- комментарий сохраняется, возвращает 201, автора и переживает повторное чтение;
- список задач проекта содержит задачу без исполнителя;
- обзор Анны не содержит архивную №10 и недоступную №11;
- обзор Бориса пуст: он не руководит проектами;
- обзор Веры содержит №11 из её собственного проекта;
- блокировка и просрочка дают причины;
- явная просьба о помощи даёт причину и цитату;
- отрицание («не нужна помощь») не даёт причину;
- более свежий нейтральный комментарий не отменяет найденную просьбу;
- собственная просьба Анны не считается;
- семидневное окно проверяется на комментариях с датами относительно
  серверного времени: свежий комментарий (через API) срабатывает, комментарий
  восьмидневной давности (фикстура в тестовой БД) — нет;
- завершённая задача отсутствует;
- сортировка: задача с тремя причинами идёт первой, при равном числе причин
  раньше идёт более ранний срок.

Тест использует существующую временную БД и сервер; рабочие данные не меняются.
Засеянные обсуждения перед проверкой окна состариваются в тестовой БД, чтобы
результат не зависел от календарной даты запуска.

### Сборка и ручной сценарий

```bash
# свежий volume отдельного Compose-проекта; рабочий volume не затрагивается
COMPOSE_PROJECT_NAME=sherpa-attention-check PORT=8099 docker compose up --build -d --wait

# API-проверки
docker compose -p sherpa-attention-check exec -T app php backend/tests/smoke.php

# сборка фронтенда (в контейнере или локально)
cd frontend && npm ci && npm run build
```

В браузере на `http://localhost:8099`:

1. Открыть обзор Анны: видны №5, №1, №2, №7 в этом порядке; №10 и №11
   отсутствуют.
2. Открыть №7, отправить комментарий, закрыть и открыть снова — комментарий
   на месте.
3. Открыть задачу из обзора, сохранить её в «Готово» — после успешного `PATCH`
   обзор обновляется, строка исчезает. Проект берётся из `detail.project_id`,
   даже если в боковом меню выбран другой проект.
4. Переключить демо-пользователя: список очищается, у Бориса обзор пуст,
   у Веры виден №11; запоздавшие ответы прежнего пользователя не применяются.
5. Проверить архив: №10 не появляется, комментарий в архивный проект отклонён.

Результаты команд и браузерной проверки фиксируются в issue с SHA.

## Допущения и ограничения

- Семь дней, набор формулировок и проверка отрицания — эвристика; возможны
  пропуски и ложные срабатывания. Цитата нужна, чтобы Анна оценила контекст
  сама. Более свежий нейтральный комментарий не снимает найденную просьбу.
- Найденная просьба не означает, что проблема ещё не решена; продукт не
  отслеживает разрешение.
- Обзор показывает только активные проекты, где пользователь одновременно
  руководитель и участник. Проекты, где он только участник, не входят.
- Демо-данные засеиваются один раз; сроки и комментарии не сдвигаются.
  Просьбы о помощи старше семи дней со временем перестанут попадать в обзор.
- Аутентификации нет; переключатель демо-пользователя остаётся открытым.
- Комментарии хранятся и показываются как обычный текст; Angular экранирует
  разметку.
